EDI integration with **SPS Commerce** via their canonical **RSX XML**
format (namespace ``http://www.spscommerce.com/RSX``, schema v7.7.0), on
top of the **OCA EDI framework** (``edi_core_oca``), targeting Odoo
19.0.

RSX is SPS's proprietary normalized schema: one document type covers
every trading partner — SPS maps each partner's native X12/EDIFACT/API
behind it, so we integrate once instead of per-partner segment maps.

X12 vs RSX: trading partners traditionally exchange **ANSI X12** files —
flat text built from positional segments (``ISA``/``GS``/``ST``/``PO1``)
and fixed-length elements. SPS translates each partner's X12 into RSX
before delivery, so the wire format this module parses and emits is
**always RSX XML** — raw X12 never reaches Odoo. (X12 *code lists* do
appear inside RSX as values, e.g. the 355 unit-of-measure and BIG
invoice-type codes.)

Documents covered:

- **Orders inbound** — RSX ``Orders`` → draft ``sale.order``
- **Shipments outbound (ASN)** — ``stock.picking`` → RSX ``Shipments``
- **Invoices outbound** — ``account.move`` → RSX ``Invoices``

All three share one group vocabulary (Address, Dates, References, Notes,
PaymentTerms, Taxes, ChargesAllowances, CarrierInformation, part-number
id block). Inbound payloads are parsed by ``services/rsx.py``
(``xmltodict``) into schema-shaped dicts; outbound payloads are rendered
by QWeb ``edi.exchange.template.output`` templates that consume the
business records directly.

Transport is pluggable per exchange record:

- **SPS-hosted SFTP** (``sftp.spscommerce.com``) via ``edi_storage_oca``
  — inbound files polled from ``out``, outbound uploaded to ``in``
  (directory names configurable on the backend);
- **Manual drop (fallback)** — import wizard for inbound, local
  directory for outbound.

This module is a POC in active development: the mappings cover the core
fields and defer the long schema tail (carrier detail, pack levels,
charges/allowances, taxes detail) to the partner implementation guide.

Configuration
=============

Dependencies
------------

Odoo modules:

- ``edi_core_oca`` — exchange framework (backends, exchange types,
  records).
- ``edi_storage_oca`` — storage-backed transport (pulls ``fs_storage``).
- ``edi_exchange_template_oca`` — QWeb output templates.
- ``sale_stock``, ``account`` — sales/delivery orders and invoices.

Python packages:

- ``xmltodict`` — inbound parser (manifest ``external_dependencies``).
- ``fsspec`` + ``paramiko`` — for the SFTP transport (via
  ``fs_storage``; ``paramiko`` must be installed manually).

Shipped configuration
---------------------

- **Backend type** ``sps_rsx``.

- **Backend** ``SPS Commerce Backend`` with the SPS directory layout::

  ::

     input_dir_pending   = out        # SPS → you (live)
     input_dir_done      = archive    # you clean "out" yourself
     input_dir_error     = archive
     output_dir_pending  = in         # you → SPS (live)
     output_dir_done     = (empty)    # SPS deletes "in" files; unused
     output_dir_error    = (empty)

- **Exchange types** (all handler roles → ``edi.sps.handler``):

+-----------------------+-----------+------------------------------+------------------+
| Code                  | Direction | Document                     | Filename         |
+=======================+===========+==============================+==================+
| ``sps_orders_in``     | input     | ``rsx.document: orders``     | ``^PO``          |
+-----------------------+-----------+------------------------------+------------------+
| ``sps_order_acks_in`` | input     | ``rsx.document: order_acks`` | ``^ACK`` (guess  |
|                       |           |                              | — confirm with   |
|                       |           |                              | SPS)             |
+-----------------------+-----------+------------------------------+------------------+
| ``sps_shipments_out`` | output    | ``rsx.document: shipments``  | ``SH-{dt}.xml``  |
+-----------------------+-----------+------------------------------+------------------+
| ``sps_invoices_out``  | output    | ``rsx.document: invoices``   | ``IN-{dt}.xml``  |
+-----------------------+-----------+------------------------------+------------------+

- **Output templates** ``sps_shipments`` / ``sps_invoices``
  (``edi.exchange.template.output`` records + QWeb views, incl. shared
  fragments ``sps_meta``/``sps_address``/``sps_item_ids``), bound via
  ``output_template_id`` on the outbound types.
- **Exchange type rules**: *Send SPS ASN* button on done pickings, *Send
  SPS Invoice* button on posted customer invoices.

Exchange-type advanced settings (``rsx:`` block):

- ``document`` — expected RSX root (orders/shipments/invoices).
- ``sender_id`` / ``receiver_id`` — RSX Meta envelope ids.
- ``outbound_dir`` — local dir for the no-storage fallback.
- ``xsd_validate`` / ``xsd_path`` — optional XSD validation of inbound
  and outbound payloads (``lxml.etree.XMLSchema``). Enable
  ``xsd_validate`` and point ``xsd_path`` at a local copy of the SPS
  schema (e.g. ``Orders.xsd``); the schemas are user-supplied, not
  shipped.

SPS SFTP map
------------

SPS hosts the endpoint at ``sftp.spscommerce.com`` with fixed directory
pairs — ``out``/``testout`` inbound, ``in``/``testin`` outbound. Create
``archive`` on the SPS account first (rename fails otherwise); we must
clean ``out`` ourselves. SPS deletes ``in`` files during processing, so
outbound types have no ``check`` handler: ``output_sent`` is terminal
until an inbound ack (997/855) arrives.

Partner and product matching
----------------------------

- **Partner**: ``res.partner.x_sps_trading_partner_id`` = the SPS
  trading-partner id (``OrderHeader.TradingPartnerId``, falling back to
  the Meta sender ids); ``res.partner.ref`` is matched and emitted as a
  fallback when the dedicated field is empty. The same id is what
  outbound templates emit in ``TradingPartnerId``.
- **Product**: ``OrderLine.VendorPartNumber``/``ApplicationId`` →
  ``default_code``; ``BuyerPartNumber`` → ``product.customer.code`` when
  installed; ``GTIN``/``EAN``/``ConsumerPackageCode`` → ``barcode``.
- **SPS references**: ``x_sps_location`` (first
  ``AddressLocationNumber``), ``x_sps_customer_ref``
  (``OrderHeader.CustomerOrderNumber``) on the sale order;
  ``x_sps_line_ref`` (first line ``References.ReferenceID``) on order
  lines.
- **UOM**: RSX carries X12 355 codes in ``OrderQtyUOM``; the
  ``edi.sps.uom.map`` table (shipped with common codes) resolves them to
  ``uom.uom`` — unmapped codes or incompatible UoMs fall back to the
  product's UoM.
- **Payment terms**: RSX ``PaymentTerms.TermsNetDueDays`` resolves to
  ``account.payment.term`` via ``edi.sps.payment.term.map`` (no rows
  shipped — map your partners' net-day values). Unmapped orders fall
  back to the customer's default payment term.

Customizing a partner
---------------------

Each SPS relationship still has a mandatory-subset profile. Point the
partner's own exchange type at a copy of the shipped
``edi.exchange.template.output`` (or extend it via ``code_snippet``) —
no code changes needed.

Usage
=====

Inbound Orders — manual drop (no storage)
-----------------------------------------

1. Open **EDI → Exchanges → Import SPS RSX**.
2. Pick the exchange type, upload the RSX ``Orders`` file.
3. The wizard creates an ``edi.exchange.record`` in ``input_pending``
   and runs receive → validate → process immediately.

Expected result: one draft ``sale.order`` per ``<Order>`` —
``PurchaseOrderNumber`` → ``client_order_ref``, ``Dates[002]`` →
``commitment_date``, one line per ``LineItem``. The exchange record is
linked as the order's EDI origin. ``TsetPurposeCode`` other than ``00``
(original) raises — cancel/change documents are handled manually for
now.

Inbound Orders — via SPS SFTP
-----------------------------

1. SPS drops a ``PO*`` file into ``out``/``testout``.
2. The storage poller creates an ``input_pending`` record; the input
   sync cron receives, validates, and processes it; processed files move
   to ``archive``.

Outbound Shipments (ASN)
------------------------

- **Manual**: open a done delivery order → **Send SPS ASN**.
- **Automatic**: ``stock.picking.button_validate`` queues a Shipments
  exchange for done pickings when the partner is enabled on the type.
- **Retrigger**: call ``picking._edi_sps_queue_shipments(force=True)``
  (server action / shell) — skips pickings with an existing record
  unless ``force``.

The picking is rendered by the ``sps_shipments`` template and uploaded
to ``output_dir_pending`` (SPS: ``in``/``testin``) as ``SH-<dt>.xml``,
or written to ``rsx.outbound_dir`` without storage.

Outbound Invoices
-----------------

Open a posted customer invoice (or credit note) → **Send SPS Invoice**.
The move is rendered by ``sps_invoices`` (``DI`` for invoices, ``CR``
for credit notes) and delivered the same way.

Extension points
----------------

- ``services/rsx.py`` — inbound codec: ``parse``/``parse_orders`` +
  ``FORCE_LIST`` for repeatable groups.
- ``edi.exchange.template.output`` — outbound documents; copy a shipped
  template per partner profile, or use ``code_snippet`` for extra render
  values.
- ``edi.sps.handler`` — handler roles; partner/product matching in
  ``_find_partner``/``_find_product``.
- ``edi.exchange.type.advanced_settings_edit`` — ``rsx.*`` config.

Known issues / Roadmap
======================

**Status:** in progress

Decisions
---------

- SPS **RSX XML** (schema v7.7.0) is the payload format — normalized
  across partners by SPS; proprietary to SPS but standard connector
  practice (cf. ``account_avatax``, ``delivery_sendcloud``).

  - Rejected: extending the raw-X12 codec in ``edi_x12_poc`` —
    per-partner segment maps duplicate work SPS already did.
  - Rejected: ``base_business_document_import``/UBL — the wire format is
    fixed by SPS.

- Module name ``edi_spscommerce``.

  - Rejected: ``edi_rsx`` — RSX is SPS's proprietary namespace; a
    generic name would overstate portability.

- Transport: **SPS-hosted SFTP** (``sftp.spscommerce.com``) via
  ``edi_storage_oca`` — ``out``/``testout`` in, ``in``/``testin`` out,
  ``archive`` for processed; no outbound ``check`` (SPS deletes ``in``
  files, ``output_sent`` terminal until an inbound ack).

  - Rejected: SPS REST API/AS2 — would need ``edi_webservice_oca`` and
    loses the file-based audit trail.

- ASN depth: ``OrderLevel`` → ``ItemLevel`` only for now — no
  ``PackLevel``/container hierarchy. SSC (SSCC) support stays on the
  roadmap for later, pending partner requirements.
- Inbound codec ``services/rsx.py`` via ``xmltodict`` — schema-shaped
  dicts (RSX element names verbatim), ``FORCE_LIST`` for ``[0..*]``
  groups; the handler does RSX→Odoo translation.
- Outbound generation via **QWeb** ``edi.exchange.template.output`` —
  templates consume ``record`` directly (mapping lives in data;
  per-partner overrides need no code). Handler injects only ``meta``.

  - *2026-11 — supersedes programmatic ``etree`` builders.*
  - *2026-11 — record-direct templates supersede ``_edi_sps_*_values``
    dict builders — one mapping surface.*

- **Batching**: ``<Order>/<Shipment>/<Invoice>[1..*]`` — plan to split
  one file into one exchange record per document (error isolation).

  - Rejected: one record per file — a bad document would block the
    batch.

- Inbound Orders create **draft** ``sale.order``; ``TsetPurposeCode``
  drives create/cancel/change (only ``00`` implemented).
- XSD validation behind ``rsx.xsd_validate`` for the test phase; schemas
  are user-supplied, not shipped.
- OCA publication: license **LGPL-3**; no vendored SPS materials (tests
  use hand-written fixtures); nominative use of the name; confirm the
  SPS agreement doesn't mark RSX confidential before publishing.

Open questions
--------------

- Which address types does the partner send (``ST``\ +\ ``BY`` only, or
  separate ``BT``)? Drives partner-matching fallback order.
- Do we get ``TsetPurposeCode`` 01/04/05 (cancel/change) or originals
  only?
- [STRIKEOUT:ASN depth: ``PackLevel``/SSCC required, or
  ``OrderLevel→ItemLevel`` enough?] — decided: ItemLevel for now (see
  Decisions).
- Invoice trigger: post of ``account.move``, or batch end-of-day?
- RSX filename convention: same ``PO``/``SH``/``IN`` prefixes +
  ``.xml``?

Plan
----

- Iteration 1 (done): module scaffold, inbound codec, outbound QWeb
  templates + skeleton mappings, SFTP/manual transports, tests.
- Iteration 2: Orders full mapping (ship-to/GLN matching, payment terms,
  UOM table, currency, notes, dropship refs); split-per-document
  receive.
- Iteration 3: Shipments full mapping (carrier/SCAC, tracking, Dates,
  References); Invoices (terms, taxes, charges/allowances).
- Iteration 4: partner profile config; verify vs SPS
  ``testin``/``testout``.
- Iteration 5: inbound acks (997/855), cancel/change order handling.
